# Nift as a build system: a qualitative engineering review

**Author:** Codex. **Date:** 11 October 2026. **Classification:** qualitative commentary, not canonical benchmark evidence.

This is my engineering assessment of implementing the same generated project with GNU Make, Ninja and Nift during the completed build-systems experiment. Preferences are subjective judgements. Observations below come from maintained definitions, capability inspection and retained authoring/correctness records. This review does not rerun the campaign, change methodology, modify Nift, or alter frozen measurements. It deliberately contains no performance ranking.

The subject is the campaign's source-built Nift v4.11.0 development snapshot, `635996b7ff5c725c81ac8ef57b1d146f7ceda642`, with suite `24671011425ef8bd0b9f05adb1c87682e9ca33b7`, GNU Make 4.4.1 and Ninja 1.13.2. Subsequent Nift work is outside this assessment. For the concurrency recommendation only, I also inspected committed/current `src/CLI.cpp` at local HEAD `9ce43cac3bddf6e5076d02da5525d424dd22a04f`; its build-option parser still has no `-j`/`--jobs` override. Unrelated uncommitted core work was not evaluated or edited.

Important limit: **all three graphs were generated by Python**, not independently hand-authored at full scale. The Nift hooks use its native process API, but the experiment does not demonstrate that replacing the generator with Nift functions, collections or filesystem code would be nicer. No Windows/macOS build, IDE integration, package-resolution workflow, long-lived team adoption or agent-comparison study was performed.

## 1. Overall judgement

**My verdict: Nift felt like a real programmable build system with a usable graph model, alongside some website-derived ceremony and native-build integration gaps.** It was not merely a website renderer running one giant shell command: each generator, object, archive and executable was a separately tracked action, and Nift scheduled their prerequisites.

Once I understood the contracts, the abstraction was coherent: a tracked item owns an output; a native script performs work; named dependencies order work; file dependencies decide whether the item is stale. The surprisingly good part was seeing successful generation, prerequisite scheduling, subsequent invalidation and blocked descendants work within that existing model. The awkward part was keeping those concepts synchronized across a tracking entry, content JSON, dependency sidecar and hook. Native compilation fits the execution model more naturally than the project's content/title/output metadata vocabulary.

This is a positive capability judgement, not a claim that the API is already the easiest way to author a C++ project.

## 2. Would I personally use it?

### Against Make

**Depends on the project; I would choose Make for a small conventional native project today.** A straightforward Makefile has less setup and a familiar target/prerequisite/recipe locality. For a repository already using Nift, particularly website publication plus native helpers or bespoke generation, I would seriously consider using Nift rather than adding another orchestrator.

For a medium C++ project with changing includes and other developers taking over, I would hesitate until compiler dependency ingestion and a clearer combined dependency-authoring path are available. That hesitation is about maintenance correctness, not measured speed. Nift's structured argument API is attractive compared with nested shell/Make quoting, but it does not remove the need to manage native toolchain conventions.

### Against Ninja

**For a generated native graph, I would choose Ninja as the backend. For bespoke directly authored automation, I would consider Nift ahead of directly authored Ninja.** I would not normally hand-maintain thousands of Ninja edges. Its intentionally restricted format is designed for generation; judging it as a disappointing general-purpose programming language would miss its purpose. See the [Ninja manual](https://ninja-build.org/manual.html#_philosophical_overview).

Nift overlaps Make as an authored orchestrator and overlaps higher-level build tools in programmability. It is not, from this experiment, a replacement for everything a CMake/Meson-like generator supplies: compiler discovery, platform configuration and established native-project conventions were not exercised. Nor did we test Nift emitting Ninja. Its clearest position here is programmable action orchestration, with native compilation one supported use.

## 3. Actual authoring effort

The representative source is [generators/native.py](../generators/native.py), especially `render()` and its nested `add()` helper. [generators/tiny.py](../generators/tiny.py) reuses the same renderer. The `implementations/` directories are not the source of three independently maintained backends.

| Encoding | Actual representation | Authoring consequence |
| --- | --- | --- |
| Make | Explicit target prerequisites, tab-prefixed recipes, `.d` inclusion | Compact rule locality; Make and shell syntax coexist |
| Ninja | Two shared rules, per-edge `action_command`, GCC depfiles/database | Predictable emitted edges; shared rules avoid needless duplication |
| Nift | Tracking entries, recipe JSON, `.deps.json`, native hook per action | Clear item identity and structured process calls, but more files and relationships |

Parameterizing 100/1k/5k/10k was equally straightforward **because Python owned the canonical action manifest**. A loop emitted each encoding. The helper code also generated source files, response files and independent oracles, so it cannot fairly be charged entirely to one build system.

Nift's process API materially helped express an argv vector, explicit cwd, launch success and exit-code handling. Most other language power was unnecessary in these hooks. Make variables/pattern rules/functions were not used to compress the graph; explicit generated rules served the fairness contract. Ninja's constraint was useful because almost no interpretation separated an emitted edge from its command.

## 4. Readability six months later

My preference would be to maintain the canonical generator and action schema rather than edit any large generated backend file. For inspecting an individual generated native action, Ninja's edge plus shared rule was the quickest map to inputs and output; Make was similarly direct but brought additional implicit-rule behavior to exclude. For modifying a procedural action, the Nift hook offered ordinary control flow and explicit results.

Another native-build developer would probably understand a small Make rule fastest. An agent would be safest changing a validated manifest and renderer, not mechanically editing thousands of tracking entries or Ninja lines. These are judgements, not measured onboarding results.

Nift's metadata is explicit, but information is less local. A prerequisite name in `depends` is insufficient to understand invalidation without reading the sidecar. The generated per-action hooks repeat boilerplate; this is our encoding choice, not proof that Nift requires a unique script for every item. A reusable context-aware hook could be investigated separately. We did not test that alternative, so I do not claim it would solve the ceremony without tradeoffs.

## 5. Debugging wrong definitions and failures

The [local certification ledger](LOCAL-CERTIFICATION.md) records actual mistakes. An unsorted expected trace was a harness bug, not a Make failure. Rename cleanup encountered Make's old depfile source reference; a later cleanup assumed Ninja's consumed depfile still existed. Those incidents made state ownership and dependency-file lifecycles concrete. They did not establish one system as unreliable.

The two rejected cloud encodings also changed my view of authoring: extra Make/Ninja recipe-marker dependencies were unnecessary, and one Ninja rule per action was a poor encoding. Both were corrected and recertified before accepted collection. They were benchmark-author mistakes, not participant shortcomings.

For a deleted source, retained CP17 logs show:

- Make names the missing source and dependent object and stops before dispatch.
- Ninja names the missing source/output edge and says there is no rule to make it.
- Nift identifies the tracked item, hook path and source location, includes the compiler error, then explicitly reports the blocked archive and executable.

Nift's causal descendant diagnostics were useful. Make/Ninja's early missing-input diagnosis was more direct for this case. Nift's hook added explicit handling of `launched` and `exit_code`; an early reserved error-code prefix was corrected to `user.build.action_failed`. That is a concrete language convention an author has to learn.

Nift already has `status` and `build -p` rebuild explanations: recommending an explanation feature as wholly missing would be wrong. We mostly used exact traces and output oracles rather than relying on human-readable explanations. Ninja documents `-d explain` and `-t query/graph/commands/targets`; I did not conduct a comparative usability trial of those tools. Native missing-target/generated-generator-failure error quality was not systematically compared, so I cannot responsibly rank it from this campaign.

## 6. Incremental mental model

Make and Ninja's native file edges were straightforward for this fixed corpus, augmented by compiler-discovered includes. Nift required one additional distinction: **completion ordering is not file invalidation**. A consumer needs the prerequisite tracked name in `depends` and the prerequisite output among its file dependencies when that output affects its result.

Once explicit, the model made sense and supported generated outputs becoming dirty within the same invocation. Before understanding it, I could easily have written a graph that orders correctly but remains incorrectly clean after a prerequisite changes. This is the largest conceptual DX footgun I encountered.

Nift's input list was exceptionally inspectable, but explicit lists are not automatically maintainable when C++ includes evolve. The experiment knew the include closure and independently audited it against compiler output. A real project needs an ongoing discovery/integration solution; the benchmark oracle is not that solution.

All three can be wrong through missing edges. The action/output oracle gave confidence beyond visual inspection. Richer semantics did not inherently prevent underspecification.

## 7. Generated files and pipelines

The common chain was specification → generated header/source → objects → archives/executable. All three represented and executed it successfully. Make's prerequisite lines and Ninja's edges communicated the native pipeline with the least incidental machinery in this encoding. Nift's named items made phase ownership clear, and native hooks let generation share its scripting/process environment with other actions.

Our header and generated source were **two separately tracked generator actions**, equally represented in all systems. That should not be mistaken for proof that one Nift action supports several declared outputs. The capability audit found a single tracked-output contract. Ninja supports multiple outputs per edge; the benchmark did not compare that facility.

For a complex procedural generation chain in a Nift-owned project, I would favor Nift if explicit inputs/outputs remain manageable. For a typical native toolchain with changing header discovery and existing generator integration, I would favor a conventional generator/backend stack. These choices reflect ownership and integration, not a claimed winner for every generation pipeline.

## 8. Targeted builds

Make/Ninja identify output targets; Nift identifies logical tracked names such as `lib/module00`. Names were deterministic and understandable here. But `nift build lib/module00` **forces the requested item**, while Make/Ninja normally bring the requested target up to date. Clean prerequisites may still be skipped in Nift.

The campaign therefore compared a dirty module, not a clean named-target no-op, and checked an untimed full followup. The forced behavior is coherent with Nift's existing CLI but surprising under ordinary native-build expectations. I would want an explicit up-to-date named-target mode, or an unmistakable documented distinction between ensure and force, before positioning it as a frictionless Make/Ninja substitution. This is a proposed API improvement, not a benchmark correction.

## 9. Concurrency ergonomics

`make -j4` and `ninja -j4` made per-invocation worker changes easy. Nift used `build-threads` in generated project configuration; 1/2/4 were deliberate values. The dependency graph correctly constrained ready work, and changing the configuration was mechanically easy for a generator.

For an individual developer adjusting load interactively, a CLI override would be nicer. I checked both the frozen and later committed/current Nift `src/CLI.cpp`: the build parser recognizes its existing modes, `-p` and `--no-process`, but does not recognize `-j` or `--jobs`. My suggestion is therefore a genuine checked gap, not an assumption from unfamiliarity. Preserve the existing configuration default, add an invocation override, and make the effective worker limit visible. No code is changed by this recommendation.

## 10. Setup and ceremony

Make needed a Makefile; Ninja needed `build.ninja`; both also used common tools, source directories and response files. Nift additionally needed project config, tracked metadata, per-action content, file-dependency sidecars and hooks. Generated/state files were part of operating Nift, whereas Ninja owned its dependency/log state and Make read compiler depfiles.

Some metadata was useful: item identity, explicit output ownership and hook location. Titles/content-extension conventions felt incidental for a compiler action. The recipe JSON duplicated argv held in the emitted hook; it satisfied the tracked-content requirement but was not read as a general action dispatcher. That duplication is specific to our adapter and would deserve a more idiomatic authoring example before judging Nift's minimum possible boilerplate.

No first-build authoring time or error-count study was recorded. File counts and my impressions must not be recast as productivity measurements.

## 11. Cross-platform potential

Demonstrated: Linux builds using G++, ar, Python and our C wrappers. Nift hooks used `cmd(arg0, arg1, ...)`, not a shell-composed command string; selecting cwd explicitly was useful and avoids one layer of shell quoting.

Inference: structured process and filesystem APIs could make portable automation easier than relying on shell utilities. **Not demonstrated:** this graph building on Windows, MSVC adaptation, path-with-spaces behavior or replacing Python generation with Nift filesystem code. Make/Ninja also have cross-platform workflows. Our Make/Ninja command emitter joins known-safe tokens, and Nift uses JSON serialization to form string literals; neither proves arbitrary-path robustness. I would review both emitters before accepting user-controlled paths.

Nift's native API is a promising portability seam, not a portability certification.

## 12. Language quality

Make combines its expansion language with shell recipes and historical conventions. In this experiment the salient conventions were tabs, `.SUFFIXES:`, disabling unwanted builtin rules/variables, and included depfiles. We did not exercise its richer functions or conditionals enough to evaluate them comparatively.

Ninja deliberately removes most programming: shared rules, variable substitution and explicit edges were a good machine-emitted representation. Complex decisions remained in Python. Its lack of general control flow is an architectural choice, not an authoring defect for its intended backend role.

Nift's assignment, conditionals, error values and structured process calls were natural enough for the short hooks. Functions, lambdas, structs, collections and imports may support reusable logic, but we did not materially use them here. I would not claim the campaign proved a superior general-purpose build language, nor that all its power was necessary to define this particular graph.

## 13. Agent experience

For initial generation, Ninja's minimal grammar was easiest to check against our manifest. Make's explicit form was also easy, with more implicit behavior to control. Nift's JSON helped mechanical generation, and its native hooks avoided embedding a shell command string, but cross-file relationships increased the number of things to verify.

For long-term maintenance, I would give an agent **the canonical graph plus assertions**, whichever backend it emits. For editing a bespoke procedural action, I would prefer a readable Nift hook over a heavily escaped Make recipe. For inspecting native dependency edges, I would prefer Ninja's explicit graph plus its native inspection tools.

We did not count escaping mistakes by format, run independent agents, or compare authoring duration. I cannot claim Nift produced the fewest mistakes. Our reserved-error-prefix issue was Nift-specific; the two comparator encoding corrections were author mistakes in Make/Ninja generation. Correctness gates mattered more than format alone.

## 14. Where Make was better

My concrete advantages for Make are tiny-project setup, local target/prerequisite/recipe readability, per-invocation worker selection, and ordinary compiler depfile integration. The rename incident also showed how existing depfiles can surprise an author; familiarity does not make state management disappear.

I would choose it when those simple native conventions fit and the project does not need extensive procedural orchestration. Familiarity/availability are additional practical reasons, but this campaign did not survey distribution availability or team expertise.

## 15. Where Ninja was better

The final shared-rule graph was straightforward to generate, inspect and map to actual native inputs. Compiler dependency ingestion worked as intended, with the consumed-depfile distinction clearly exposed during cleanup. Output-oriented target selection and a small declarative model were comfortable backend contracts.

Its documented query/graph/command tools and multiple-output/command-change facilities are attractive integration features; they were not all directly exercised. I would use Ninja for the large generated graph even under equal-speed assumptions because that is exactly the boundary it is designed to own. That is distinct from wanting to hand-author complex project policy in Ninja.

## 16. Where Nift was better

The strongest demonstrated DX points were:

1. **Structured native action code:** argv, cwd, launch status and exit status in an ordinary hook, with explicit error handling.
2. **Named graph execution with causal failures:** tracked actions genuinely scheduled generation and native work; failed prerequisites explicitly blocked descendants.
3. **A coherent extension of the existing project model:** the same tracked machinery can own rendered pages and native actions without delegating the graph to a hidden Make/Ninja runner.

The third point supports mixed-project adoption, but this native benchmark did not itself build a combined website/native repository. Full filesystem automation, shared high-level functions and eliminating all helper languages remain potential benefits. We still used Python generators and C instrumentation, so “one tool replaced everything” would be false.

## 17. Prioritized improvements

These are subjective adoption priorities, not assertions of general defects or requests to modify core here.

### P0 — adoption blockers for particular native projects

- **Compiler-discovered dependency integration or a supported maintained bridge.** Static include lists worked for the canonical corpus; I would hesitate to adopt that maintenance burden for a changing medium/large C++ project. It does not block every Nift use.
- **One unambiguous dependency-authoring path.** Ordering versus invalidation must remain explicit internally, but an author should not accidentally express only half the intended edge. A combined declaration/helper plus validation would reduce the risk.

No inability to express the tested graph was found. These are maintenance/adoption concerns, not failed capability gates.

### P1 — major improvements

- **Named-target ensure-versus-force ergonomics**, preserving a deliberate force operation.
- **Per-invocation worker override**, confirmed absent in the inspected CLI.
- **Idiomatic reusable native-action authoring**, reducing metadata/argv duplication without hiding dependencies or adding a replacement scheduler.
- **Supported multi-output action ownership** for tools producing related outputs in one process. The tested two-action workaround is not a universal solution.
- **Better graph inspection and command preview integration**, building on existing status/rebuild explanations. Ninja-like inspection is a reference, not a claim that Nift has no diagnostics.

### P2 — polish

- Native-build examples that use artifact/action vocabulary alongside existing page/content terms.
- Clear discoverability of supported user error-code conventions and effective concurrency.
- Examples covering paths with spaces, response files, missing inputs and safe definition changes.

Performance optimization is intentionally left to the separate core handover.

## 18. Practical project recommendations

I would confidently consider Nift for Linux bespoke generation/automation in an existing Nift project, or a website repository with a few native helper artifacts, provided its dependencies are explicit and tested. The experiment supports the underlying execution capability; the mixed workflow recommendation is an inference.

I would still choose Make for a tiny conventional C/C++ build. For a substantial native application, I would usually choose an established native-project generator with Ninja, especially when platform/toolchain configuration and include discovery matter. Cross-platform monorepos, remote caches, hermetic builds and package integration were outside scope; I would not recommend Nift for those merely because this DAG passed.

An agent-maintained repository benefits from a clear graph, deterministic definitions and validation. Nift may fit well, but being agent-maintained alone is not enough reason to select it.

## 19. Is “build system” fair?

**Yes, with caveats.** The tested implementation tracks inputs/outputs, detects stale work, executes custom native actions, schedules prerequisite DAGs concurrently, supports targeted closure, propagates failures and verifies produced outputs. Those are substantive build-system capabilities.

The caveats concern ergonomics and integration: explicit compiler-header inputs, single-output ownership, forced named-target behavior, additional tracking ceremony and untested broader native-project workflows. “Build system” is technically defensible; “drop-in replacement for a mature native build stack” is not established by this experiment.

## 20. Defensible positioning

Nift is a programmable tracked-action build system that also supports website generation. It can orchestrate native tools and generated artifacts through named dependency graphs and native scripts, using explicit file inputs for incremental invalidation. It is a plausible choice for bespoke automation and mixed Nift projects. Developers evaluating it for larger native projects should examine dependency-discovery integration, target semantics and toolchain/platform requirements rather than assume it supplies an established native build ecosystem.

## 21. Decision matrix and equal-performance counterfactuals

These choices deliberately ignore the campaign's speed results.

| Situation | My choice | Why |
| --- | --- | --- |
| Tiny hand-written native build | Make | Least ceremony for conventional file rules |
| Medium conventional hand-written native project | Make, or a native generator with Ninja | Familiar native dependency/toolchain workflows; Nift requires more authoring discipline |
| Huge generated native graph | Ninja backend | Clear generated execution boundary and compiler dependency integration |
| Complex generated pipeline in a Nift project | Nift, conditionally | Native action scripting and named ordering; check changing inputs and multi-output needs |
| Cross-platform automation-heavy project | Evaluate Nift against established options | Structured APIs are promising; our Linux evidence does not settle portability |
| Agent-maintained conventional C++ project | Validated generator + Ninja | Mechanical graph checking and existing native integration |
| Agent-maintained bespoke mixed workflow | Nift candidate | Readable procedural hooks and a shared project model, with explicit contracts |
| Compiler/native-project-generator backend | Ninja | Deliberately designed for that role |
| Website + native helpers already owned by Nift | Nift | Avoid an additional graph owner when supported semantics suffice |

**If performance were equal tomorrow, would I prefer Nift over Make?** For bespoke automation and an already-Nift mixed project, often yes. For a small conventional native build, no. For a medium changing C++ project, dependency integration and declaration ergonomics still decide it.

**If performance were equal tomorrow, would I prefer Nift over directly authored Ninja?** For nontrivial procedural project logic, yes, provisionally: Nift has a more suitable authored programming surface. For a compact static edge list, Ninja is perfectly reasonable. Equal performance would not make me replace an existing generator→Ninja boundary with Nift without another benefit.

**If performance became comparable to Ninja while retaining Nift's current capabilities, how compelling would it be?** A serious candidate for programmable orchestration, particularly mixed and bespoke projects. It would remove one reason to hesitate but would not resolve include discovery, multi-output actions, force-versus-ensure semantics or ecosystem integration. I would want those addressed before an unconditional native-project recommendation.

## 22. What the checklist misses

The useful surprise was that failure blocking and same-invocation generated invalidation were real contracts, not features improvised in the benchmark runner. The frustrating surprise was how easy it was to think a prerequisite name also expressed file invalidation. My view changed from “verify whether this can orchestrate native work at all” to “it can; now improve the authoring boundary.”

We did not need a hidden scheduler, recursive Make architecture or clever Ninja tricks. We also did not need most of Nift's richer language constructs. Future DX evaluation should use a small directly authored project that evolves over weeks: add an include, change a compiler flag, introduce one multi-output generator, rename an artifact, onboard a second author and adapt to a second platform. That would test maintenance rather than static graph generation. This is a recommendation only; no new campaign is started.

Finally, separate the benchmark runner's complexity from the product's complexity. Fixture restoration, action logging, hash equality, sampling and rejected-attempt retention consumed much effort but were common experimental responsibilities. They do not show that ordinary Nift, Make or Ninja use requires a benchmark harness.

## Follow-up: tracked graphs vs .build.f authoring

This follow-up corrects the scope of the original authoring assessment. The campaign exercised a Python-generated tracked-item encoding. It did not establish that this encoding is Nift's minimum, natural or best authoring surface. The original assessment above remains as a record; the qualifications and revised choices below supersede its broad conclusions about ceremony and backend preference.

This is qualitative reasoning from the frozen capability audit, adapter source and documented scripting/lifecycle contracts, with direct script dispatch checked in frozen `src/CLI.cpp` at `635996b7ff5c725c81ac8ef57b1d146f7ceda642`. It adds no measurements, prototype, independent agent trial or portability certification. Benchmark code, results, evidence and Nift core are unchanged.

### Two authoring models, with different responsibilities

**Model A: tracked declarative graph.** Tracked metadata identifies artifacts; `depends` orders completion; ordinary file dependencies determine invalidation; discovered or explicit lifecycle scripts implement actions. This is the model exercised by the campaign. It is useful when the build engine should own incremental checks, prerequisite scheduling and output lifecycle.

**Model B: authored procedural scripts.** A project can instead organize logic in `build.f`, `tasks/test.f`, `tasks/package.f` and reusable functions, using tracked items only where incremental artifact ownership is useful. Existing direct path execution already supports `nift build.f`; no new command spelling is required. Per-artifact discovery such as `content/about.build.f`, `content/about.pre-build.f` and `content/about.post-build.f` supplies a different entry point with tracked-item context.

A top-level script is a reasonable home for source discovery, argument construction, platform conditions, optional components, validation and related developer tasks. Per-artifact hooks are a reasonable home for producing or validating a particular output. Both can coexist. Moving logic into one script does **not** automatically give its subprocesses native tracked scheduling, incremental checks or failure propagation between artifact nodes: the script must either implement those responsibilities or delegate them to the tracked build. Fewer files alone are not evidence of an equivalent build engine.

The benchmark's recipe JSON duplicated argv embedded in generated hooks. That duplication is an adapter choice, not a necessary Nift contract. Likewise, emitting a separate hook per action was not proof that reusable hooks or discovery conventions cannot work. Some metadata remains necessary when incremental ownership is wanted, including the current requirement for tracked content even for a custom output-producing hook. That requirement deserves evaluation on its own merits rather than being bundled with every file the adapter generated.

### Useful explicitness versus redundant ceremony

I withdraw “more ceremony” as an unconditional disadvantage. The relevant question is whether each declaration adds meaning and makes mistakes detectable.

| Declaration | Distinct semantic role | What can currently be checked, and what remains uncertain |
| --- | --- | --- |
| Tracked item and output | Artifact identity, output path and ownership | A custom build must leave its tracked output as a regular file; this is not a proof that every possible ownership conflict is rejected |
| `depends` | Prerequisite completion ordering | Unknown names, self edges, duplicate edges and cycles are rejected before building |
| Ordinary file dependencies | Inputs whose changes make an artifact stale | Declared/discovered inputs participate in checks; arbitrary subprocess reads are not automatically inferred |
| Build hook | How the artifact is produced | Hook failure stops that item's later phases and blocks dependent actions; successful output validation does not prove the declared input set is complete |
| Pre/post hooks | Lifecycle phase and associated responsibilities | Phase sequencing and failure behavior have defined contracts |

These are different facts. An agent can inspect an ordering field without parsing a command string to discover its intended role. A generator can rewrite an input list without editing a shell recipe. Structured records can support focused diffs and independent checks. That is a plausible safety advantage even when the canonical representation is longer.

It is also a limited advantage today. Rejecting a cycle does not detect a missing input dependency. A compiler that reads an undeclared header can still produce an incorrectly considered-clean output. JSON structure is not a blanket guarantee of a typed, complete or contradictory-definition-free build contract. Broader ownership checks and consistency linting should be demonstrated before being credited as existing features.

**Bad ceremony** is duplicated information without additional meaning, manually synchronized values, inconsistent boilerplate, or implementation-driven metadata with no useful contract. **Useful explicitness** is action identity, artifact ownership, declared inputs, completion dependencies, invalidation dependencies, lifecycle phase and output path. The design goal should be explicit semantics, with concise authoring helpers that produce or validate a canonical representation. Minimizing line count is secondary to minimizing ambiguity and synchronization hazards.

### Keep ordering and invalidation distinct

The split is conceptually sound. An action may need a prerequisite to finish without consuming its output bytes; an input file may affect freshness without being produced by another tracked action. Combining these concepts internally would lose that distinction.

My earlier footgun criticism should therefore be read as an ergonomics and discoverability criticism. A higher-level “B consumes A's output” helper could derive both the completion edge and ordinary file dependency from one authored relationship. Separate order-only and file-only declarations should remain available. This reduces repeated authoring without pretending the two derived facts mean the same thing. It is a design suggestion, not an existing helper demonstrated by this campaign.

### Nift can own authoring policy as well as execution

An external Python generator is not intrinsically required. Nift's file-writing and subprocess facilities make a standalone script that prepares graph files before invoking a separate build a plausible architecture. However, this review did not certify a supported graph-construction API or an idiomatic end-to-end self-generation workflow. Producing JSON files is less convenient than a validated artifact/consumption API, and authors must correctly handle serialization, paths and regeneration inputs.

In particular, editing tracking metadata from a running artifact hook must not be assumed to alter the already-loaded scheduler safely. Graph preparation should precede execution. Tracked hooks also have different constraints from standalone scripts, including restrictions on process-global cwd/environment changes. There is no basis here for claiming in-process dynamic graph mutation or treating the two contexts as interchangeable.

This leaves a coherent potential product shape: procedural scripts express project policy; a tracked graph supplies incremental artifact contracts. Nift could own both. It could also generate or invoke Ninja where a specialized backend is useful, although that coexistence was not tested. There is no permanent architectural requirement for Python to sit between them.

### Where the Make comparison changes

I still prefer Make for a tiny conventional native build consisting of a few straightforward file rules. Familiarity and existing compiler dependency integration are practical benefits, not a universal reward for terseness.

The crossover is when procedural policy becomes the substantial part of maintenance: source discovery, platform branches, optional components, code generation, packaging, tests and custom validation. At that point I would generally prefer ordinary `.f` control flow, shared functions and structured `cmd(...)` calls to increasingly interleaved Make expansion and shell recipes, subject to the APIs needed by the project being supported. That preference applies to agent edits as well as human edits. It is a qualitative judgment, not a measured productivity result.

Project size alone does not locate this crossover. A medium project with boring native rules may benefit more from established native tooling; a small project with complicated packaging policy may benefit from Nift scripting immediately. Procedural authoring improves the policy layer without removing the need for reliable compiler input tracking.

### Native integration gaps and target UX

Compiler dependency ingestion is a serious **C/C++ integration gap**. For a medium or large project with changing transitive includes, manually maintaining include closure is not an acceptable default. It can be an adoption blocker there. It is not a fundamental objection to Nift as a general build/task system, nor does it invalidate the ordering/invalidation model.

Depfile support could be a bounded native-tool integration, but a correct implementation needs escaping, path resolution, stale/missing inputs, generated headers and persistence semantics. It should not be described as merely reading a list after compilation. It would remove a major hesitation for ordinary C/C++, while multi-output ownership, target UX and toolchain integration would still matter.

Both ensure and force operations are useful. Current named builds force the requested item while checking prerequisite closure; that behavior should remain available. I would add an explicitly documented ensure operation rather than silently change existing semantics. No syntax or implementation change is proposed here.

Graph inspection is also an improvement area, not a complete absence of diagnostics: existing `status` and `build -p` already provide information. Rich graph queries and explanations, a CLI worker override and reusable authoring examples would improve the maintenance surface. Multi-output actions are an engine-model extension; depfiles and native project tooling are integration work. None of these gaps proves explicit tracking is the wrong abstraction.

### Agent authoring and generated backends are separate questions

For an agent modifying a bespoke workflow, I would usually prefer structured `.f` scripting to a complex Makefile with shell quoting and implicit expansion behavior. For an agent generating a large static graph, I would prefer a validated generator with a schema and invariant checks over unconstrained edits to either Ninja or tracked JSON. The extra records in a tracked representation could help automated review, provided those checks actually exist.

Directly authored Ninja is a third case: a compact edge list can be appropriate, but Ninja is intentionally a generated execution backend, as its [manual](https://ninja-build.org/manual.html) explains. Comparing Nift's programming surface with Ninja's manifest is different from comparing Nift with the generator that owns project policy above Ninja.

The original review leaned too heavily toward the benchmark's generated-backend setting. A generator plus Ninja remains attractive today for native work. Under equivalent supported semantics and operational reliability, however, an integrated Nift authoring/execution environment does not need an extra backend simply because Ninja is familiar.

### Revised decision matrix and maturity counterfactual

The counterfactual below assumes the requested package of improvements: no-op within roughly 20% of Ninja, compiler depfile ingestion, a consumption helper, ensure/force targeting, CLI worker override, graph query/explain tooling, reusable `.build.f` examples and multi-output actions. These are assumptions, not new findings. Performance parity alone would not imply correctness or operational maturity.

| Situation | Present-day judgment | Under the stated mature-Nift counterfactual |
| --- | --- | --- |
| Tiny conventional native build | Make remains reasonable | Make remains reasonable; Nift if already the project runtime |
| Moderately procedural build/tasks | Prefer Nift scripting when required APIs suffice | Prefer Nift over increasingly complex Make policy |
| Medium changing C/C++ project | Native generator/Make with reliable include tracking; Nift needs integration work | Nift is a credible choice if native ecosystem requirements are modest |
| Agent-maintained bespoke workflow | Prefer inspectable `.f` policy plus checked artifact contracts | Prefer Nift over complex Make or directly authored Ninja |
| Huge generated graph with simple custom policy | Ninja is the conservative backend choice | No inherent requirement for Ninja if Nift's necessary semantics and reliability are comparable |
| Conventional C++ needing established project integrations | Prefer an appropriate native generator, often targeting Ninja | Still favor that ecosystem when its integrations save substantial work |
| Website, assets, native helpers and developer tasks sharing a Nift project | Nift is compelling where supported contracts suffice | Strong case for one runtime and project model |

**Would I choose mature Nift over Make?** Often yes once project policy is substantially procedural or shared with other Nift tasks. Tiny conventional builds are not obliged to migrate.

**Over hand-authored Ninja?** Usually yes for authored project logic. A short fixed manifest or existing stable generator can still make Ninja a sensible choice.

**Over CMake/Meson → Ninja?** Sometimes. The remaining reasons to choose those systems are their project tooling and ecosystem, rather than an inherent need to separate generator and executor. For example, CMake documents [toolchain and capability handling](https://cmake.org/cmake/help/latest/manual/cmake-toolchains.7.html), while Meson documents [IDE introspection](https://mesonbuild.com/IDE-integration.html), [dependency facilities](https://mesonbuild.com/Manual.html) and [installation workflows](https://mesonbuild.com/Installing.html). Those capabilities are outside this counterfactual's build-engine improvements. If a project does not need them, and Nift covers its semantics, there is no remaining architectural reason in this review to insist on generator → Ninja. Existing integrations, migration cost and proven reliability still need project-specific assessment.

A shared website/scripting/build/task runtime has real engineering value when it eliminates duplicated path policy, language boundaries and lifecycle coordination. It becomes feature accumulation when each subsystem retains separate conventions or when missing specialized capabilities require extensive replacement tooling. The tradeoff flips according to integration saved versus integration rebuilt.

**Revised verdict:** retain the rich explicit model; remove duplicated/no-information authoring; provide helpers above precise canonical contracts. The benchmark established useful execution behavior and exposed current integration gaps. It did not establish that Nift's best authoring UX is the benchmark adapter, that agents benefit from terseness, or that a mature Nift must retain Ninja as its executor. Those parts of the original framing needed correction.

### Current preference

Yes: that reading accurately represents my current judgment. Today I would often choose Make for a tiny conventional native build, and Nift for bespoke procedural automation, agent-maintained bespoke workflows, and website/assets/native-helper/task projects where its APIs and artifact contracts fit. I would prefer Nift's authored `.f` policy to complex directly authored Ninja. For larger conventional C/C++ today, reliable compiler dependency ingestion, engine maturity and surrounding native tooling keep established generators/backends attractive. Under the stated mature-Nift counterfactual, with comparable required semantics, reliability and performance, my remaining preference for CMake/Meson → Ninja would primarily concern their native ecosystem and project integrations, not an inherently superior executor architecture. Depfiles alone do not establish that counterfactual. Preserve explicit ownership, ordering, invalidation and lifecycle contracts; improve validation and add concise helpers rather than collapse distinct semantics to reduce file or line count.
